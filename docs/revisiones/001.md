## 4. Hallazgos

### 4.1 [CRÍTICO] `gridCols` no se interpola en `LandingHero.astro` — rompe el layout de 2 columnas en 19 páginas

`src/components/landing/LandingHero.astro:73`:

```astro
<div class="grid items-center gap-12 lg:grid-cols-[{gridCols}]">
```

`{gridCols}` está dentro de una cadena de atributo `class="..."` normal
(comillas dobles), no dentro de un *template literal* (backticks +
`${...}`). Astro no interpola expresiones `{}` dentro de una cadena
literal — solo cuando la expresión completa es el valor del atributo o
está dentro de backticks. El resultado: **la cadena `{gridCols}` se emite
tal cual, siempre, sin importar qué valor tenga el prop.**

Verificado contra la build (`npm run build`, `dist/`):

```
$ grep -o 'class="grid items-center gap-12[^"]*"' dist/productos/smart-pba/index.html dist/sectores/manufactura/index.html dist/nosotros/index.html dist/productos/index.html
dist/productos/smart-pba/index.html:class="grid items-center gap-12 lg:grid-cols-[{gridCols}]"
dist/sectores/manufactura/index.html:class="grid items-center gap-12 lg:grid-cols-[{gridCols}]"
dist/nosotros/index.html:class="grid items-center gap-12 lg:grid-cols-[{gridCols}]"
dist/productos/index.html:class="grid items-center gap-12 lg:grid-cols-[{gridCols}]"
```

Y confirmado que Tailwind no genera ninguna regla para esa clase inválida
(`grep -o "grid-cols-\[[^]]*\]" dist/_astro/*.css` no devuelve nada en todo
el CSS del sitio). Comparado contra el código anterior al refactor
(`git diff`), el original tenía `lg:grid-cols-[1.2fr_1fr]` — una clase
Tailwind válida y funcional que sí generaba la regla CSS correspondiente.

**Impacto:** en escritorio (`lg:` y superior), las 16 páginas que ya
existían y usaban este patrón de hero de 2 columnas
(`productos/[slug]` ×3, `servicios/[slug]` ×7, `sectores/[slug]` ×5,
`nosotros` ×1) pierden la división de columnas: el texto y la columna
derecha (lista de puntos clave, figura de imagen del sector) quedan
apilados verticalmente en vez de lado a lado. Es una regresión visual real
en páginas que **ya funcionaban correctamente antes de este plan** — el
propio plan exigía "no rediseña el contenido... visualmente" (§2) como
condición explícita. En los 3 hubs nuevos y en `nosotros.astro` el efecto
práctico es inofensivo por coincidencia (piden una sola columna,
`gridCols="1fr"`, y el resultado accidental — sin ninguna regla
`grid-cols` — también es una sola columna), pero es el mismo bug: no
funciona por diseño, funciona por casualidad.

**Corrección sugerida:** usar un *template literal* interpolado, igual que
ya hace correctamente `CrossSellCierre.astro:60`
(`class={\`mt-12 grid gap-5 ${itemsGridCols}\`}`):

```astro
<div class={`grid items-center gap-12 lg:grid-cols-[${gridCols}]`}>
```

**Por qué no se detectó:** el build no falla (es un bug semántico, no de
compilación) y el criterio de aceptación "Revisión manual en móvil y
escritorio de las 3 páginas hub y de una landing de cada tipo" (§8 del
plan) exigía precisamente la verificación visual que habría revelado esto
de inmediato. No hay evidencia en el diff de que se haya ejecutado.

### 7.1 [CRÍTICO — sigue sin resolverse] `gridCols`: la sintaxis de Astro se corrigió, pero el layout de 2 columnas sigue roto

**Lo que se corrigió:** `src/components/landing/LandingHero.astro:73` pasó
de una cadena literal (`class="... lg:grid-cols-[{gridCols}]"`, el bug
original) a un *template literal* correctamente interpolado:

```astro
<div class={`grid items-center gap-12 lg:grid-cols-[${gridCols}]`}>
```

Verificado contra la build: el HTML generado ahora sí muestra el valor
real de cada página, no el texto `{gridCols}`:

```
dist/productos/smart-pba/index.html:  lg:grid-cols-[1.2fr_1fr]
dist/sectores/manufactura/index.html: lg:grid-cols-[1.08fr_0.92fr]
dist/nosotros/index.html:             lg:grid-cols-[1fr]
dist/productos/index.html:            lg:grid-cols-[1fr]
```

Esto es exactamente lo que pedía la corrección — el bug de Astro (props no
interpolados) está resuelto.

**Por qué el defecto reportado sigue presente:** el HTML ya es correcto,
pero **Tailwind nunca genera la regla CSS para esas clases**, y por lo
tanto el layout de 2 columnas sigue sin renderizarse en escritorio — el
mismo síntoma visual de la primera revisión, con una causa distinta.

Verificado contra la build (mismo método que en §4.1 original, repetido
tras el fix):

```
$ grep -o "grid-cols-\[[^]]*\]" dist/_astro/*.css | sort -u
(sin resultados)

$ grep -c "1\.2fr_1fr\|1\.08fr_0\.92fr\|grid-cols-\[1fr\]" dist/_astro/*.css
0  (los tres archivos CSS)
```

Cero coincidencias — ninguna de las tres variantes de `grid-cols-[...]`
que usa el sitio tiene una regla generada en ningún archivo CSS del build.

**La causa:** Tailwind v4 (vía `@tailwindcss/vite`, `astro.config.mjs:12`)
genera CSS escaneando el **texto fuente literal** de los archivos en busca
de nombres de clase completos — no ejecuta Astro ni evalúa props en tiempo
de build. La clase `lg:grid-cols-[${gridCols}]` que aparece en el código
fuente de `LandingHero.astro` no es, para el escáner de Tailwind, ninguna
de las tres clases reales que terminan en el HTML (`lg:grid-cols-[1.2fr_1fr]`,
`lg:grid-cols-[1.08fr_0.92fr]`, `lg:grid-cols-[1fr]`) — el escáner solo ve
el texto literal `lg:grid-cols-[${gridCols}]`, que no es una clase válida,
así que no genera ninguna regla. Esto es una limitación conocida y
documentada de Tailwind (evitar construir nombres de clase de forma
dinámica/interpolada; los nombres de clase deben aparecer completos y
literales en alguna parte del código fuente que el escáner lea). Es un
patrón distinto al bug original, pero el resultado observable —el hero de
producto/servicio/sector/nosotros no se divide en 2 columnas en
escritorio— es idéntico.

Confirmado que la corrección aplicada a `CrossSellCierre.astro:60`
(`class={\`mt-12 grid gap-5 ${itemsGridCols}\`}`, señalada como ejemplo
correcto en la primera revisión) **tiene exactamente el mismo problema**:
al no pasar por un `safelist` ni aparecer completa en el código fuente,
tampoco genera CSS para sus valores (`sm:grid-cols-2`,
`sm:grid-cols-2 lg:grid-cols-3`) — con una salvedad importante: esas dos
clases en particular (`sm:grid-cols-2`, `lg:grid-cols-3`) **sí existen en
el CSS final**, pero no por esta interpolación, sino porque son clases
completas y literales que ya aparecen escritas en otras partes del sitio
(`ServiciosGrid.astro:15`, `Sectores.astro`, etc.) — Tailwind las generó
igual por casualidad, no porque la interpolación de `CrossSellCierre`
funcione. Con `LandingHero` no hay ese colchón: `1.2fr_1fr`,
`1.08fr_0.92fr` y `[1fr]` como valor de `grid-cols` no aparecen escritos
como clase completa en ningún otro lugar del código, así que no hay nada
que los genere por accidente.

**Corrección exacta pendiente:** en todo el código solo se usan 3 valores
distintos de `gridCols` (`1.2fr_1fr` por defecto, `1.08fr_0.92fr` en
sectores, `1fr` en nosotros y en los 3 hubs) — confirmado por
`grep -rn 'gridCols=' src/pages/`. La forma correcta de resolverlo es que
esas 3 clases completas aparezcan **literalmente** en el código fuente de
`LandingHero.astro`, para que el escáner de Tailwind las encuentre. Por
ejemplo, mapear el prop a una clase completa en vez de interpolar el
valor dentro de la clase:

```astro
const gridColsClass: Record<string, string> = {
  '1.2fr_1fr': 'lg:grid-cols-[1.2fr_1fr]',
  '1.08fr_0.92fr': 'lg:grid-cols-[1.08fr_0.92fr]',
  '1fr': 'lg:grid-cols-[1fr]',
};
```
```astro
<div class={`grid items-center gap-12 ${gridColsClass[gridCols]}`}>
```

(o, alternativamente, un `safelist` en la configuración de Tailwind con
las 3 clases — la tabla de arriba es más simple porque no depende de tocar
configuración global y deja todo el mapeo a la vista en el propio
componente). Cualquiera de las dos soluciones sirve; lo que no funciona es
seguir interpolando el valor arbitrario dentro de la clase.

**Verificación pendiente tras la próxima corrección:** repetir
exactamente el mismo comando (`grep -o "grid-cols-\[[^]]*\]" dist/_astro/*.css`)
y confirmar que las 3 variantes aparecen con al menos una regla
`grid-template-columns` cada una — no basta con que el HTML se vea bien,
hay que confirmarlo en el CSS generado.

### 8.1 [Resuelto] `gridCols`: ahora sí genera CSS

`src/components/landing/LandingHero.astro:57-63` implementa exactamente
la corrección que pedía §7.1 — un mapa de valores a clases completas y
literales:

```astro
const gridColsClass: Record<string, string> = {
  '1.2fr_1fr': 'lg:grid-cols-[1.2fr_1fr]',
  '1.08fr_0.92fr': 'lg:grid-cols-[1.08fr_0.92fr]',
  '1fr': 'lg:grid-cols-[1fr]',
};
```

y el `<div>` del grid usa `class={\`grid items-center gap-12
${gridColsClass[gridCols]}\`}` (línea 81) — el valor interpolado en tiempo
de ejecución ahora es siempre una de las 3 clases completas, y esas 3
clases aparecen escritas literalmente en el código fuente, que es lo que
necesita el escáner estático de Tailwind para generarlas.

**Nota metodológica:** el primer intento de verificar esto con
`grep -o "grid-cols-\[[^]]*\]" dist/_astro/*.css` volvió a dar cero
resultados — no porque la regla no exista, sino porque Tailwind escribe
los selectores CSS con los caracteres especiales escapados
(`.lg\:grid-cols-\[1\.2fr_1fr\]`, con barras invertidas literales antes de
`:`, `[`, `.`, `]`), y ese patrón de `grep` no las contempla. Es el mismo
tipo de falso negativo que ya corrigió §7.4 para `VisualCiudades`, esta
vez en la propia verificación del revisor, no en el código del
desarrollador. Se rehízo la búsqueda con un script Node que compara
substrings exactos, incluidos los caracteres de escape:

```
$ node checkcss.js
BaseLayout.D9kL7N5W.css 1.2fr_1fr      => FOUND: grid-cols-\[1\.2fr_1fr\]{grid-template-columns:1.2fr 1fr}
BaseLayout.D9kL7N5W.css 1.08fr_0.92fr  => FOUND: grid-cols-\[1\.08fr_0\.92fr\]{grid-template-columns:1.08fr .92fr}
BaseLayout.D9kL7N5W.css 1fr            => FOUND: grid-cols-\[1fr\]{grid-template-columns:1fr}
```

Las 3 reglas existen, con la declaración `grid-template-columns` correcta
cada una, en `BaseLayout.D9kL7N5W.css` — el bundle CSS compartido que
cargan todas las páginas del sitio (confirmado en `03-codigo.md`, hallazgo
4.2, que ya documentaba este bundle único). El HTML compilado sigue
mostrando las clases correctas por página (`lg:grid-cols-[1.2fr_1fr]` en
producto, `lg:grid-cols-[1.08fr_0.92fr]` en sector,
`lg:grid-cols-[1fr]` en nosotros y en los 3 hubs) y ahora, a diferencia de
la segunda revisión, esas clases sí tienen una regla CSS que las respalda.
**Resuelto — verificado end-to-end (HTML + CSS generado), no solo a nivel
de código fuente.**
