### 2. `Escape` cierra el menú móvil y los dropdowns — con un hallazgo

**Caso simple (abierto por clic), verificado con espera suficiente para
que termine la transición CSS de 200ms:**

```
A: open, aria-expanded = true, visible = True
A: after Escape (500ms wait), aria-expanded = false, visible = False,
   computed opacity = 0, computed visibility = hidden
```

**Caso difícil (abierto por Tab, con `:focus-within` activo — la razón de
ser de `dropdown-suppressed`), mismo resultado:**

```
B: focus-open, aria-expanded = true, visible = True
B: after Escape (500ms wait), aria-expanded = false, visible = False,
   computed opacity = 0, computed visibility = hidden, focus is trigger = True
```

El mecanismo que describe el plan §3.1 (agregar `dropdown-suppressed` para
ganarle a `:focus-within` en el empate de especificidad, porque el foco
vuelve al disparador) **funciona exactamente como se diseñó**: sin esa
clase, el panel quedaría visualmente abierto pese a `aria-expanded=false`;
con ella, cierra de verdad. Menú móvil, mismo patrón:

```
mobile_menu_aria_expanded_after_open: true
mobile_menu_visible_after_open: True
mobile_menu_aria_expanded_after_escape: false
mobile_menu_visible_after_escape: False
focus_after_mobile_escape_is_toggle: True
```

**Hallazgo [IMPORTANTE] — `dropdown-suppressed` no se limpia con
`mouseenter`/`focusin`, solo con `mouseleave`/`focusout`:**

Secuencia reproducida (headless, determinista):

```python
trigger.focus()                    # abre por teclado (:focus-within)
page.keyboard.press('Escape')      # cierra correctamente (ver arriba)
page.hover(trigger)                # pase de mouse genuino, SIN clic
```

Resultado:

```
after real mouse hover, group classes = group relative dropdown-suppressed
  | aria-expanded = true | panel visible = False
```

`aria-expanded` vuelve a `"true"` (el `mouseenter` sí lo actualiza), pero
el panel **permanece invisible** porque `dropdown-suppressed` sigue
presente en el `.group` — nunca hubo un `mouseleave` real que lo limpiara,
porque el dropdown se abrió por teclado, no por mouse, así que ese `.group`
jamás disparó `mouseenter`/`mouseleave` antes del `Escape`. El resultado es
exactamente el tipo de discrepancia que el punto 1 de este mismo plan
buscaba eliminar: un lector de pantalla anunciaría el panel como
expandido mientras un usuario de mouse no ve nada.

**Recuperación parcial ya existente:** un **clic** sobre el disparador en
ese mismo estado sí lo arregla (el *handler* de `click` limpia
`dropdown-suppressed` de todos los grupos incondicionalmente antes de
abrir):

```
after click-recovery, aria-expanded = true, panel visible = True
```

Así que el atasco no es permanente ni requiere recargar la página —pero
sí es real para cualquier usuario que, tras cerrar con `Escape`, intente
seguir con el mouse en vez de con clic.

**Causa raíz:** el diseño de §3.1 del plan solo contempla limpiar
`dropdown-suppressed` en `mouseleave`/`focusout` ("una vez que el usuario
efectivamente se aleja"). No contempló el caso de un *reingreso* genuino
(`mouseenter`/`focusin`) sin que haya habido una salida previa registrada
por JS para ese grupo. Es un vacío del propio plan, no una desviación del
desarrollador — el código implementado corresponde exactamente a lo
especificado en §3.1.

**Corrección recomendada** (una línea por evento, en el mismo bloque de
`Header.astro` que ya agrega los listeners de `mouseenter`/`focusin`):

```js
group.addEventListener('mouseenter', () => {
  group.classList.remove('dropdown-suppressed');
  setExpanded(group, true);
});
group.addEventListener('focusin', () => {
  group.classList.remove('dropdown-suppressed');
  setExpanded(group, true);
});
```

(Hoy esos dos listeners solo llaman a `setExpanded(group, true)`, sin
tocar `dropdown-suppressed` — ver `Header.astro`, bloque agregado en el
`<script>`.)

### 2.1 [MENOR — hallazgo nuevo, no bloqueante] `aria-expanded` puede quedar en `"false"` mientras `:focus-within` mantiene el panel visible

Al extender la prueba más allá de la secuencia original, se probó qué
pasa si el mouse se aleja del disparador **sin que el foco de teclado se
mueva** (el foco quedó en el botón tras el `Escape` del paso 2, y nada lo
saca de ahí entre el paso 3 y este paso):

```
5) after moving mouse away again: aria-expanded = false | visible = True
   | group classes = group relative
```

`mouseleave` fija `aria-expanded=false` de forma incondicional, sin
comprobar si `:focus-within` sigue vigente — y en este caso sí sigue
vigente (el foco de teclado nunca se movió), así que el panel permanece
visible por CSS mientras el atributo ARIA dice lo contrario. Es una
inconsistencia real, pero de naturaleza distinta y más leve que el
hallazgo original:

- No hay ningún estado atascado: en cuanto el foco se mueve a cualquier
  otro lugar (`focusout` con `relatedTarget` fuera del grupo), todo se
  sincroniza correctamente — confirmado en el mismo log, línea "7)"
  (`blur` seguido de `focus`, resultado consistente).
- El contenido sigue siendo alcanzable por teclado y por mouse en todo
  momento; lo único incorrecto es el valor anunciado de `aria-expanded`
  para un lector de pantalla durante esa ventana específica.
- Requiere una combinación deliberada de modalidades (mantener el foco de
  teclado en el botón mientras se mueve el mouse por separado), menos
  frecuente que la secuencia original (que solo requeria usar Escape y
  luego seguir con el mouse, algo mucho más común).

**Causa raíz:** los cuatro *listeners* (`mouseenter`/`mouseleave`/
`focusin`/`focusout`) fijan `aria-expanded` de forma independiente según
el evento que los disparó, en vez de recalcular el estado visual real
(unión de `:hover`, `:focus-within` y `.is-open`, menos
`dropdown-suppressed`) cada vez. Corrección sugerida para un futuro plan
de accesibilidad (no se aplica aquí porque no bloquea este veredicto):

```js
const syncExpanded = (group) => {
  const trigger = group.querySelector('[data-dropdown-trigger]');
  const visible =
    (group.matches(':hover') || group.matches(':focus-within') || group.classList.contains('is-open'))
    && !group.classList.contains('dropdown-suppressed');
  trigger?.setAttribute('aria-expanded', String(visible));
};
```

y llamar `syncExpanded(group)` desde los cuatro listeners en vez de
`setExpanded(group, true/false)`.

### 4. Honeypot invisible para un humano y funcional contra bots

Verificado contra el HTML/CSS compilado y con interacción real, no solo
lectura de código:

- **Invisibilidad:** `#website` está envuelto en `.hp-field`
  (`position: absolute; left: -9999px; width: 1px; height: 1px; overflow:
  hidden`, confirmado en el CSS compilado) — su *bounding box* real en
  pantalla es `x: -9342`, muy fuera del viewport en cualquier resolución.
  El contenedor tiene `aria-hidden="true"` y el input `tabindex="-1"`.
- **Fuera del orden de tabulación:** `Shift+Tab` desde el campo "Nombre"
  no aterriza en `#website` (confirmado que el elemento anterior en el
  orden de tabulación no es el honeypot).
- **Funcional contra bots (simulado):** con el formulario mínimamente
  lleno y `#website` relleno programáticamente (como haría un bot que
  completa todos los campos del DOM sin evaluar CSS), al enviar:
  - El mensaje de estado mostrado es el de éxito
    ("¡Gracias! Hemos recibido su solicitud..."), **el mismo texto que
    especifica el honeypot** en `Contacto.astro` — no el mensaje
    "Se abrió WhatsApp..." que dispararía la rama normal sin
    `FORM_ENDPOINT` configurado. Esto confirma que se tomó la rama del
    honeypot, no la rama real de envío.
  - No se disparó ninguna petición de red ni apertura de WhatsApp
    asociada al envío.

**Correcto.**
